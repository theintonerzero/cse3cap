## Part 1 · CAP-32, security posture review

**Criteria (as raised in `docs/Security-Review.md`):** F2, F3 and F4 are decided and
recorded, and whatever is decided is built.

**Skills:** `/write-adr` for #44, `/add-endpoint` is **not** needed (no route changes),
`superpowers:test-driven-development` for F4.

**Branch:** `fix/CAP-32-token-posture`.

### Findings (read 2026-09-30)

- `api/config/sanctum.php:53`: `'expiration' => null`.
- `api/config/sanctum.php:68`: `'token_prefix' => env('SANCTUM_TOKEN_PREFIX', '')`, so the
  prefix is empty unless `.env` sets it.
- `api/database/seeders/DemoSeeder.php:113-123`, `issueTokens()`: `createToken('demo')` with no
  abilities and no expiry, and it **skips any user who already has a token**. So changing the
  config affects only tokens minted afterwards. The three tokens already on the shared
  database stay unprefixed and never expire until someone revokes and reissues them, and
  the README says reissuing breaks everyone's setup at once.
- `web/src/session/tokens.ts` keeps pasted tokens in `sessionStorage` and names F2 and F3 as
  the reason. Any decision here should update that comment.
- `scripts/check-bundle-secrets.sh` greps the built bundle for a canary string. A prefix gives
  it, and any secret scanner, a real shape to look for.

### Task 1.1 · F4, prefix new tokens (build it)

**Files:** `api/config/sanctum.php`, `api/.env.example`, `api/tests/Feature/TokenPrefixTest.php`
(new), `scripts/check-bundle-secrets.sh`, `docs/Security-Review.md`.

- [ ] **Red.** Add `TokenPrefixTest`: create a user, call `createToken('demo')`, and assert
  `plainTextToken` starts with the prefix and that Sanctum still authenticates it on
  `GET /api/v1/auth/me` (200). Run `./run test`; it fails on the prefix assertion.
- [ ] **Green.** Default the config to a project prefix, e.g.
  `env('SANCTUM_TOKEN_PREFIX', 'rdiary_')`, and add the key to `api/.env.example` with a
  comment. The prefix is not a secret; it exists so the token is recognisable.
- [ ] **Bundle check.** In `check-bundle-secrets.sh`, also fail on any match for the prefix
  followed by a token-shaped tail in the built assets, beside the existing canary grep.
  Check that it can fail: put a prefixed literal in a throwaway module, see the check fail,
  then revert.
- [ ] **Existing tokens.** Do **not** revoke or reissue the shared database's tokens from
  this branch. The shared-database rules forbid it without saying so first. Write down in the
  PR, and raise at standup, that the three live tokens stay unprefixed until the team picks a
  moment to reissue them together.
- [ ] **Verify.** `./run test`, `./run check`. Quote both results in the PR.

### Task 1.2 · F2 and F3, decide them (ADR #44, Proposed)

**Files:** `docs/adr/architecture-decision-records.md`, `docs/Security-Review.md`,
`web/src/session/tokens.ts` (comment only, if the decision changes what it says).

- [ ] Load `/write-adr`. Draft **ADR #44, Status: Proposed**, covering both findings:
  - **F2, expiry.** Options: keep `null` for the MVP and record the date that stops being
    defensible (the public demo, CAP-26); a config `expiration` in minutes, which expires
    the three seeded tokens on everyone at the same moment; or a per-token `expires_at`
    passed to `createToken()` in the seeder, reissued on a known schedule. Recommend one and
    say what reissuing costs the team.
  - **F3, abilities.** Watch for this trap: **authorisation lives in `api/app/Policies/`
    and nowhere else** (CLAUDE.md). Enforcing abilities through `tokenCan()` in middleware or
    controllers would create a second place authorisation lives. The ADR has to either keep
    `['*']` on purpose (policies are the boundary; abilities would only limit what a leaked
    token can do) or say exactly where a check like `read-only` would live without breaking
    that rule. Recommend keeping `['*']` unless the team wants read-only demo tokens for
    CAP-26.
- [ ] Mark F2, F3 and F4 in `docs/Security-Review.md` with where each was decided or fixed,
  in the same quoted-note style as F5 to F9 (for example "Fixed in CAP-32, PR #n").
- [ ] **Done in Jira only when** #44 is Accepted by the team **and** anything it decides to
  build is merged. If only F4 merges, CAP-32 stays In Progress and a comment records the
  split (`/jira-tickets`, partial tickets).

## Part 2 · CAP-22, end-to-end journey test

**Criteria (from the import):**
1. Student creates a reflection, writes every entry, self-scores, is refused an incomplete
   submit with the offending entries named, then submits.
2. Assessor sees it in the queue, is forced to comment when scoring below the student,
   counter-scores every entry, and the reflection flips to assessed on its own.
3. The radar renders both polygons from real rows afterwards.
4. Runs against a seeded test database in CI. Never against the shared instance: the suite
   runs `migrate:fresh` and five people share that box.

**Skills:** `superpowers:brainstorming` for the infrastructure (then ADR #45 via
`/write-adr`), `/add-screen` for reference on the client and screens (no screen changes are
expected), `/seed-data` before touching any seeder.

**Branch:** `test/CAP-22-journey`.

### Findings (read 2026-09-30)

- ADR #42 keeps per-screen specs in `web/e2e/` against `web/e2e/fake-api.ts`, and says
  outright: *"CAP-22's journey keeps its own design. It is the check that needs a real
  backend."* So the journey must **not** use the fake, and must not live in `web/e2e/`, where
  `playwright.config.ts` would pick it up with the fake's routing.
- CI (`.github/workflows/ci.yml`) already has a **Backend** job with its own `mysql:9.7`
  service and `DB_CONNECTION: mysql_test`. That is the pattern to copy. There is no job
  that serves the API over HTTP.
- The contract has about 30 operations; the fake serves 11. The journey needs, against the
  real API: `GET /auth/me`, `GET /gigs/{id}`, `POST /reflections`, `PATCH /entries/{id}`,
  `POST /entries/{id}/evidence`, `PUT /entries/{id}/scores/self`,
  `POST /reflections/{id}/submit`, `GET /review-queue`, `POST /entries/{id}/scores`,
  `GET /me/radar` (methods checked against `docs/openapi.yaml`).
- Token handoff: there is no login screen (ADR #15). The app reads tokens from
  `sessionStorage` keys `reflection-diary-tokens` and `reflection-diary-active-slot`
  (`web/src/session/tokens.ts`). The journey can write CI-minted tokens there through
  `page.addInitScript`, one browser context per role. These tokens are minted fresh in CI
  against a throwaway database and printed nowhere, so no real credential ever reaches a
  browser.
- `DemoSeeder` gives students, an assessor and gigs. `ReflectionSeeder` pre-writes
  reflections, which would collide with the one the journey creates (CLAUDE.md, ADR #37). The
  journey seeds **`DemoSeeder` only**, and uses a student and sprint with no reflection yet.

### Task 2.1 · Decide the infrastructure (ADR #45, Proposed)

- [ ] Brainstorm, then record in ADR #45: a new CI job `journey` (MySQL service,
  `migrate:fresh --seed --seeder=DemoSeeder`, `php artisan serve`, `vite preview` or
  `vite dev` pointed at it); how the tokens are minted (an artisan command or tinker one-liner
  that prints JSON for the run only, never committed); a separate
  `web/playwright.journey.config.ts` with `testDir: './journey'`; and a `./run journey`
  command that **refuses to run** unless `DB_HOST` is `127.0.0.1` or `localhost` and the
  database is not `reflection_diary`. `scripts/guard-shared-db.sh` is a PreToolUse hook for
  agents' shell commands and `api/tests/TestCase.php` guards PHPUnit only, so neither covers
  a person typing `./run journey`. The command needs its own check.
- [ ] Say in the ADR what it costs: CI time (the Frontend job went from 16s to 1m17s for
  Chromium alone, per ADR #42) and a second Playwright config to maintain.

### Task 2.2 · Harness

**Files:** `web/playwright.journey.config.ts`, `web/journey/support.ts` (new),
`web/package.json` (`test:journey`), `run` (`journey` subcommand, with the local-only check
from Task 2.1).

- [ ] Config: no retries (same reasoning as `playwright.config.ts`), `baseURL` set to the
  Vite origin, and the API base taken from the environment.
- [ ] `support.ts`: `as_role(browser, slot, token)` returns a page whose init script sets
  the two `sessionStorage` keys. No token literal anywhere in the repository.
- [ ] Locally: `./run journey` against a local MySQL only. Show the guard refusing the
  shared host before relying on it.

### Task 2.3 · The journey spec, criteria 1 to 3

**File:** `web/journey/student-assessor.spec.ts`.

- [ ] **Student:** Diary home → gig → create reflection → every entry: narrative, evidence,
  self-score → try to submit with one entry left incomplete: assert the refusal names that
  entry (the submit gate's `details`, rendered by the stepper) → complete it → submit → land
  on the Submitted screen.
- [ ] **Assessor:** review queue shows the reflection → counter-score one entry lower than
  the student without a comment: assert the `COMMENT_REQUIRED` refusal is shown → add the
  comment → counter-score every entry → assert the reflection reads as assessed without
  anyone pressing anything else (`Scoring.php` closes it).
- [ ] **Radar:** as the student, Diary home's radar has two polygons, and their values match
  `GET /me/radar` fetched in the test. Assert that the numbers match, not only that SVG exists.
- [ ] **Prove it can fail:** break one link in the chain in a throwaway commit (for example,
  skip the comment step) and see the spec go red. Revert it, and say in the PR what was
  broken.

### Task 2.4 · CI and docs

- [ ] Add the `journey` job to `ci.yml`, keeping traces of a failed run for a week like the
  Frontend job does.
- [ ] Update `docs/Frontend-and-Backend.md` (the journey is the one check that crosses the
  seam) and the README's commands list. Update CLAUDE.md's "Tests and checks" paragraph only if the
  team wants it (it is a rules file).
- [ ] **Done in Jira only when** criteria 1 to 4 are each checked against the merged spec
  and a green CI run of the new job is linked.

## Part 3 · CAP-21, four-states audit

**Criteria (from the import):**
1. Every screen shows loaded, loading, empty and error. Loading is a skeleton, never a spinner.
2. The error state shows the envelope's message and switches on `code` where it matters,
   especially the submit gate, which reports which entries failed.
3. A checklist in the PR with a screenshot per state per screen.
4. Anything missing is fixed here. Nothing is deferred out of this ticket.

**Skills:** `/add-screen` (four states, tokens, client), the `playwright` plugin for
screenshots at phone and desktop widths.

**Branch:** `fix/CAP-21-four-states`. Start after #70 (CAP-36) merges, because it changes
`EntryStepper.tsx`.

### Findings (read 2026-09-30, a first grep and not the audit)

Nine screens in `web/src/screens/`: DiaryHome, GigDetail, EntryStepper, Submitted,
ReviewQueue, SelectFramework, EditFramework, HistorySheet, ExportSheet.

- Every screen except **ExportSheet** uses `Skeleton`. ExportSheet's comment says it
  deliberately shows "a live status, not the loading skeleton" while an export runs. The
  audit decides whether that is this ticket's loading state or a separate state that still
  needs a skeleton for the initial load.
- The three "spinner" matches (DiaryHome, EntryStepper, Submitted) are comments saying
  "not a spinner". No spinner was found.
- Only EditFramework (`edit-framework.spec.ts`) and Submitted (`submitted.spec.ts`) have
  per-screen Playwright specs for all their states. The rest rely on `scripts/verify-*.sh`
  greps, which ADR #42 says cannot prove a state renders.

### Task 3.1 · The audit, written down first

- [ ] For each screen × state, record: reachable (yes/no), how (fixture or fault), what it
  shows, whether it switches on `code`. Keep the table in the PR description, not in a new
  doc (CLAUDE.md, documentation).
- [ ] Build against seeded data: `/add-screen` says which seeded student to use for which
  state. Screenshots come from the fake API (`web/e2e/`), so no token goes into a browser.

### Task 3.2 · Specs for the states that lack them

- [ ] One spec per screen still missing one, in `web/e2e/<screen>-states.spec.ts`, following
  `submitted.spec.ts`: loaded, loading (a delayed route shows the skeleton), empty, and error
  (a `Fault` injected by name). Extend `fake-api.ts` only with response shapes, never with
  rules (ADR #42).
- [ ] Red first: each new spec fails against a deliberately removed state, then passes.

### Task 3.3 · Fixes

- [ ] Fix every gap the audit found, in this ticket (criterion 4). The submit gate's error
  must list the failing entries: check the stepper against `SubmitGate.php`'s `details` shape
  in `docs/openapi.yaml`.
- [ ] `./run e2e`, `./run check`, and the screen's `./run verify-*` script. Screenshots at
  phone and desktop widths go into the PR checklist (criterion 3).
- [ ] **Done in Jira only when** every row of the table is ticked with a screenshot and
  merged.
