Reflection Diary API

A competency reflection and scoring service. Students write reflections per sprint, score themselves against a swappable rubric, and a supervisor or assessor counter-scores. The record belongs to the student.

http://localhost:8000/api/v1
Auth
Bearer token (Sanctum)
Contract

Database
MySQL 9.7.2 LTS, shared, TLS

Getting a response

The API runs locally against the shared database. There is nothing to install for MySQL: everyone points at the same instance.

cd api
php artisan serve

curl -H "Authorization: Bearer $JANE" \
     http://localhost:8000/api/v1/auth/me

If you would rather not wait for the backend, the contract mocks itself and returns the same seeded data used below:

npx @stoplight/prism-cli mock docs/openapi.yaml --port 4010
If a request fails with Access denied

Suspect TLS before the password. The server refuses unencrypted connections and PDO does not negotiate TLS unless handed a CA file, so a missing MYSQL_ATTR_SSL_CA surfaces as an authentication failure. The CA is committed at db/letsencrypt-roots.pem and config/database.php anchors the path to the application root.

Authentication

Every route requires Authorization: Bearer <token>. There is no login endpoint and there will not be one: identity belongs to the host platform, and the MVP authenticates with three seeded tokens.

The three tokens

Issued by php artisan db:seed --class=DemoSeeder, which prints them once. Sanctum stores only a hash, so a token cannot be recovered afterwards. The values are pinned in the team channel, never in the repository.

Sam is on one gig deliberately. If every token saw every gig, nothing would prove that authorisation resolves per gig rather than globally.

Roles and permissions

The client never sends a role. Not in a header, not in the body, not in a query parameter. A client-supplied role is a client-supplied permission. Roles resolve server-side from gig_participants, for the specific gig in question, because the same person can be a student on one gig and an assessor on another. There is no role column on users.

Educator is not a distinct role. It maps to supervisor, which already exists.

Authorisation lives in policies and nowhere else. A policy denies as not found rather than forbidden whenever the caller should not learn the resource exists, so a gig you do not participate in and a gig id that does not exist return byte-identical responses.

Errors

One envelope for every non-2xx response, including 401 and 404. It is registered centrally, so no controller can return a different shape.

{
  "error": {
    "code": "NOT_FOUND",
    "message": "No such resource, or it is not yours.",
    "details": {}
  }
}

details is always an object. Switch on code; never parse message.

StatusMeansCodes
400Validation or a business rule refused itVALIDATION_FAILED, CONTEXT_REQUIRED, COMMENT_REQUIRED, LEVEL_NOT_IN_COMPETENCY, EVIDENCE_REQUIRED, NARRATIVE_REQUIRED, SELF_SCORE_MISSING, FILE_TYPE_NOT_ACCEPTED, FILE_TOO_LARGE, FRAMEWORK_NOT_ASSIGNED
401Missing or invalid tokenUNAUTHENTICATED
403You can see it, but your role may not do thisROLE_FORBIDDEN
404No such thing, or it is not yoursNOT_FOUND
409Conflict with something that already exists or a state you are not inDUPLICATE_REFLECTION, DUPLICATE_ASSIGNMENT, ALREADY_SCORED, NOT_DRAFT, NOT_SUBMITTED, FRAMEWORK_IN_USE

The list is exhaustive. A response carrying a code that is not here is a bug in the endpoint, not an undocumented feature.

Why 404 says so little

One code covers both “no such thing” and “there is one, but it is not yours”. A second code would tell the caller which, and that is the leak. The three 409 codes come from distinct unique indexes in the database, so the API can tell you exactly which constraint you hit without inventing a rule the schema does not enforce.

Endpoints

Thirty endpoints, all live. The contract and the router are compared mechanically and agree exactly, and everything below has been driven end to end over HTTP with real bearer tokens.

Frameworks

GET /frameworks live

Available rubrics. created_by is null for a seeded base template and set for someone's copy, which is how the framework picker groups them. in_use is derived from whether any reflection references it, never stored.

[
  { "id": "d7018d17-9547-11f1-9b81-f227eb28d537", "fw_key": "latrobe6",
    "version": "v1",  "name": "La Trobe six-competency",
    "is_active": true, "created_by": null, "in_use": false },
  { "id": "d70190aa-9547-11f1-9b81-f227eb28d537", "fw_key": "sfia9",
    "version": "9.0", "name": "SFIA 9",
    "is_active": true, "created_by": null, "in_use": false }
]

Accepts ?active=true. Once in_use turns true the framework is permanently read-only: editing one would silently change what past students were scored against.

GET /frameworks/{framework_id} live

The full rubric, nested. This drives the entry stepper, the radar axes and the framework editor.

      "levels": [
        { "id": "…", "level_value": 1, "descriptor": "Emerging — acts when prompted." },
        { "id": "…", "level_value": 4, "descriptor": "Advanced — shapes the work and lifts others." }

}
The same endpoint, a different rubric

Ask for SFIA 9 and you get "scale": { "min": 1, "max": 7 }, seven levels per competency and a populated category. The axis count, the scale and every descriptor change with no code change on either side. That is the point of storing the rubric as data, and it is a definition-of-done item for the whole project.

scale is read from the v_framework_scale view rather than computed in PHP, because a SFIA skill is valid over only part of the seven-point scale and the bounds belong to the level rows.

Reflections

POST /reflections live

Start one, on a gig or a sprint. Send gig_id, sprint_id, or both. A sprint already knows its gig, so sending both and disagreeing is refused rather than guessed at.

One entry is created eagerly per competency, so the stepper can say “3 of 6” before anything is written. The framework version is snapshotted here and the framework is frozen from this moment.

{ "sprint_id": "11111111-aaaa-4111-8111-111111111111" }
→ 201, the full nested reflection with six empty entries

Refusals: CONTEXT_REQUIRED when neither id is given, FRAMEWORK_NOT_ASSIGNED when the gig has no rubric, DUPLICATE_REFLECTION when one already exists for that context, 403 for anyone who is not a student on the gig.

GET /reflections live

Newest first, filtered by gig_id, sprint_id or status. A student sees their own; an assessor, supervisor or employer sees every reflection on the gigs they are on.

GET /reflections/{reflection_id} live

The screen payload, and the same shape for the student's stepper and the assessor's. What differs is what each may do with it, and that is decided by policies rather than by hiding fields.

{
  "id": "…", "status": "assessed", "framework_version": "v1",
  "owner": { "id": "…", "display_name": "Jane N" },
  "entries": [{
    "id": "…", "competency_code": "contribution", "position": 1,
    "narrative": "Paired on the importer…",
    "evidence": [{ "kind": "link", "label": "The pull request", "uri": "…" }],
    "scores": [
      { "scorer_role": "self",     "scorer_class": "self",
        "level_value": 3, "comment": null,  "scorer": { "display_name": "Jane N" } },

        "level_value": 2, "comment": "Solid, more to do on testing.",
        "scorer": { "display_name": "Sam O" } }
    ]
  }]
}
PATCH /entries/{entry_id} live

The autosave endpoint. The frontend debounces into it. Owner only, draft only.

POST /entries/{entry_id}/evidence live

A link as JSON, a file as multipart. Type and size are checked against the rubric's policy, not a global setting, so one gig can accept a screenshot and another can insist on a PDF. DELETE /evidence/{evidence_id} removes one while the reflection is still a draft.

POST /reflections/{reflection_id}/submit live

The gate. Every entry needs a narrative and a self-score, plus evidence if the rubric requires it. It refuses on the first rule that fails and names the offending entries, because the stepper sends the student straight to them.

{ "error": {
    "code": "NARRATIVE_REQUIRED",
    "message": "Every competency needs something written before you can submit.",
    "details": { "entry_ids": ["…", "…"] } } }

After it passes, the reflection is read-only. Editing an entry, deleting the record or submitting again all return 409 NOT_DRAFT. DELETE /reflections/{id} works on a draft and never afterwards, which is part of the ownership promise.

GET /reflections/{reflection_id}/events live

The history, newest first. Append-only, and notifications are derived from it rather than stored separately.

Scoring

PUT /entries/{entry_id}/scores/self live

The student's own score, and a PUT deliberately: changing your mind before submitting is part of reflecting, so it replaces rather than adding a second row.

POST /entries/{entry_id}/scores live

Everyone else's. The reflection must be submitted first. One score per scorer per entry, so a repeat is ALREADY_SCORED and there is no re-scoring in the MVP.

The response says whether that score was the one that completed the reflection:

{ "level_value": 2, "scorer_class": "counter", …,
  "reflection_status": "assessed",
  "completed_the_reflection": true }
GET /review-queue live

Submitted reflections awaiting your score, with per-row progress. A gig can have both an assessor and a supervisor, and a reflection one of them has scored is still work for the other.

One consequence worth knowing

The last counter-score flips the reflection to assessed, and an assessed reflection is in nobody's queue. So on a gig with two counter-scorers, whoever finishes first closes it for the other. That follows from the two rules as specified rather than from a defect, but it is worth confirming with the client that it is what they want.

Analytics

GET /me/radar live

Self against counter, per competency. Scope mirrors the UI: sprint_id gives that sprint's true comparison, gig_id the latest within a gig, neither the latest across the record.

{
  "scope": { "gig_id": null, "sprint_id": null },
  "framework": { "fw_key": "latrobe6", "scale_min": 1, "scale_max": 4 },
  "axes": [{ "code": "contribution", "short_label": "Contrib.", "position": 1,
             "self": 3, "counter": 2, "counter_role": "supervisor" }]
}

An axis appears for every competency in the rubric, scored or not, so the shape of the chart does not change as scores arrive.

Why the unscoped radar names a framework

A student on two gigs can be scored against two rubrics whose competency codes do not overlap at all, so “the whole record” would mean twelve axes and no meaning. The framework of the most recent reflection wins, and the response says which, so the chart is always coherent and the caller can always tell what they are looking at.

GET /me/progress live

The same two numbers along the sprints of one gig, which is what turns a snapshot into a trend. gig_id is required.

GET /me/calibration live

Self minus counter. A positive gap means the student rated themselves higher than the person assessing them did, which is the conversation the screen exists to start. Null until both sides have scored.

[{ "competency_code": "contribution", "self_level": 4,
   "counter_level": 2, "counter_role": "assessor", "gap": 2 }]
GET /me/coverage live

Competencies you have never been scored on, in rubric order. framework_id is required. Scored rather than evidenced, because evidence is optional per rubric and requiring it would report gaps that are not gaps.

Export

POST /exports live

Ask for the record as a file. Returns 202 with whatever the row actually says: on a synchronous queue the job has already run and it reads complete; on a real worker it reads pending. Poll GET /exports/{id} until it is complete or failed.

reflection_id exports one reflection; omitting it exports everything.

GET /exports/{export_id}/download live

The file itself, served through the API rather than as a link, so the policy runs on every fetch. Export is “own” for every role in the matrix, so not even a supervisor on the gig can read one, and the refusal is 404.

The file carries the framework version snapshotted on each reflection, not the rubric's current version. What the student was scored against is the whole point of an exportable record.

The business rules

Seven rules carry the product. Each has exactly one implementation, and this is where it lives.

RuleImplemented in
The submit gate: narrative, self-score, evidence if the rubric asksSubmitGate
A comment is required when a counter-score is below the student's ownScoring
The level must belong to the entry's competencyScoring
A framework referenced by any reflection is permanently read-onlyFrameworkEditing
A gig is scored against one rubric, never twoFrameworkAssigner
One entry per competency, created eagerly with the reflectionReflectionCreator
Assessed once every entry carries a counter-scoreScoring

The third is the one the database cannot help with. scores.level_id points at a level and a level points at a competency, but nothing stops a level from a different competency being attached to an entry. Without the check a student could score “Advanced” on Collaboration using the Leadership descriptor, and the radar would show a number nobody ever meant.

Testing it

The suite

110 feature tests against real MySQL, not sqlite: the schema uses generated columns, CHECK constraints and window functions that sqlite cannot express, so an in-memory suite would be testing a different database from the one we ship on.

cd api && php artisan test

They test the denials, not just the permissions. A policy that returns true for everyone passes every happy-path test ever written.

The smoke script

The suite proves the rules in isolation with Sanctum::actingAs. That cannot see wiring: middleware order, the guest redirect, content negotiation, anything that only exists once a request crosses HTTP. So there is a script that drives the whole product with the three real tokens.

cd api && php artisan serve &
./scripts/smoke.sh

It writes a reflection as Jane, submits it through the gate, counter-scores it as Sam, watches it flip to assessed, reads all four analytics endpoints, then exports and downloads the record, checking the refusals on the way past. 51 checks, each printing the status it got against the status it wanted, so a failure names the call that broke.

It picks a sprint Jane has not used yet, so you can run it more than once against the same database.

The mock

The contract mocks itself, with the seeded data as examples, so the frontend can build against every endpoint before touching the backend:

npx @stoplight/prism-cli mock docs/openapi.yaml

It returns 401 without a bearer token and the documented example with one.

The contract cannot drift

The operations docs/openapi.yaml declares and the routes the application serves are compared mechanically, and they agree exactly: thirty for thirty. An endpoint added without its contract entry, or a contract entry with no endpoint behind it, shows up as a mismatch rather than as a frontend bug three weeks later.

Conventions

Names

snake_case in the database, in JSON and in the generated frontend types. There is no mapping layer anywhere, so a column called uri is a field called uri. A field renamed on the way out is a bug, not a convenience.

Identifiers and time

Every id is a char(36) UUID. Timestamps are ISO 8601 in UTC, 2026-08-14T03:20:00Z. The database stores DATETIME(6) throughout and never TIMESTAMP, which stops working in January 2038 — this product is a record meant to outlive that.

Pagination

None. Result sets are small at MVP scale, and a student has one reflection per sprint per gig.

The contract is the agreement

docs/openapi.yaml is the machine source of truth. The frontend generates its types from it and mocks against it; the backend implements it. It describes exactly the endpoints that exist, so the mock is a truthful stand-in rather than a wish list. Any change to an endpoint updates the contract in the same commit.

Not built yet

The API is complete. Two things are deliberately outstanding, listed so nobody builds against something that is not there.

ThingWhere it stands
PDF export The schema and the contract both allow pdf, and exports.format accepts it. Rendering one needs dompdf, and adding a package is the team's decision rather than something to slip into a commit, so POST /exports refuses pdf clearly instead of quietly producing JSON.
The frontend A Vite scaffold in web/ that renders one word, and no screens. The contract mocks itself, so every endpoint on this page can be built against today.

Also worth deciding before the demo: whether completing a reflection should close it for every scorer, or only for the one who finished. The current behaviour follows the specification exactly, and is described under the review queue above.
